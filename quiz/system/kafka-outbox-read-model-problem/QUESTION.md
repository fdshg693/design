# 問題:注文イベントを「確実に出して、正しく反映する」(Kafka中級)

- 前提となる問題: [kafka-order-events-problem](../kafka-order-events-problem/QUESTION.md)(読んでいなくても解ける)
- 回答: `ANSWER.md`

## 背景

フードデリバリーサービス「はやメシ」では、前回の設計どおり注文イベントを Kafka で配信し始めた。
コンシューマ側(キー・パーティション数・グループ・コミット)は順調に動いている。

ところが運用を始めて1か月で、次のような問い合わせ・障害が届いた。

1. **「注文は確定しているのに、店舗のタブレットに注文が来ない」** という問い合わせが週に数件ある。
   調べると、該当の注文は注文DBには存在するが、Kafka に `CREATED` イベントが**1件も出ていなかった**
2. 逆に、**注文DBに存在しない注文** の `CREATED` イベントが Kafka に流れていたことがあった(配達割当サービスがエラーログを出していた)
3. 売上集計サービスがコンシューマのリバランス後に**同じ注文の売上を2回計上**し、日次の売上レポートが合わなくなった
4. 注文サービスがイベントに項目を追加してデプロイしたところ、**売上集計サービスがパースエラーで停止**した

さらに今回、Kafka のイベントを使って次の2つの機能を新しく作ることになった。

- **注文状況画面**(ユーザーアプリ):「店舗が受付済み」「配達中」などを表示する。表示用の最新状態を Redis に持つ
- **店舗向け注文検索**(店舗管理画面):過去の注文を期間・状態・金額などで検索する。OpenSearch に索引を作る

**あなたの仕事は、これらの問題を解消し、新機能のデータ反映を設計すること**である。

## 現在の構成

```
                       ┌──────────────┐
 [ユーザーアプリ] ──> │ 注文サービス │ ──(①DB更新)──> [注文DB: PostgreSQL]
                       │              │ ──(②produce)─> Kafka topic: order-events (40パーティション, key=order_id)
                       └──────────────┘                     │
                                                            ├─> [通知サービス]
                                                            ├─> [配達割当サービス]
                                                            ├─> [売上集計サービス] ──> [集計DB: PostgreSQL]
                                                            ├─> (新規)[注文状況サービス] ──> [Redis]
                                                            └─> (新規)[注文検索サービス] ──> [OpenSearch]
```

### 注文サービスの現在の実装(擬似コード)

```python
def change_order_status(order_id, new_status):
    with db.transaction():
        order = db.select_for_update("orders", order_id)
        order.status = new_status
        order.version += 1
        db.update("orders", order)
    # ↑ ここでコミット済み
    kafka.produce("order-events", key=order_id, value=make_event(order))
```

## 確定済みの前提(考えなくてよい)

| 項目 | 内容 |
|------|------|
| Kafka | マネージドKafka、ブローカー3台。`order-events` は40パーティション、key=`order_id`、保持期間7日 |
| プロデューサー設定 | `acks=all`、`enable.idempotence=true` |
| コンシューマの基本方針 | 前回の設計どおり、サービスごとに別グループ、処理後に手動コミット(at-least-once)、失敗し続けるものは DLQ |
| 注文DB | PostgreSQL(マネージド)。論理レプリケーション(WAL を外部から読む機能)を有効にできる |
| 周辺ミドルウェア | Kafka Connect(Debezium を含む)、Schema Registry をマネージドで利用できる |
| イベントの中身 | `event_id`(UUID)、`order_id`、`user_id`、`store_id`、`type`、`occurred_at`、`total_amount`、および注文の `version`(上記擬似コードの `orders.version`) |
| 集計DB | 売上集計サービス専用の PostgreSQL。他サービスからは使わない |

## 要件・数値

- ピーク時:注文 **120 件/秒**、状態変更イベント **600 件/秒**(前回と同じ)。1年後に2倍を見込む
- **注文DBに確定した状態変更は、必ず Kafka にイベントとして出ること**(欠損ゼロ)
- **注文DBでロールバックされた変更は、イベントとして出てはならない**
- 注文DBの更新からイベントが Kafka に出るまでの遅延は、通常時 **1秒以内** が目標
- **注文状況画面(Redis)**:古い状態に戻って見えてはならない(「配達中」の後に「受付済み」に戻る、など)。Redis が全損しても数十分以内に復旧できること
- **店舗向け注文検索(OpenSearch)**:最大 **2年分** の注文を検索できること。反映遅延は数秒〜数十秒でよい
- **売上集計**:同じイベントを何度受け取っても、売上は**1回だけ**計上されなければならない(こちらは「なるべく」ではなく必須)
- **イベントのスキーマ変更**:今後も項目の追加は頻繁にある。プロデューサーとコンシューマを**別々のタイミングでデプロイ**しても止まらないこと

## 設問

1. **二重書き込み問題**
   - 背景の問題1・2は、現在の実装でそれぞれどんなタイミングに障害が起きると発生するか。「DB更新 → Kafka送信」の順(今の実装)と、「Kafka送信 → DB更新」の順に入れ替えた場合のそれぞれについて説明せよ
   - なぜ「両方成功したらOK、失敗したらリトライ」では解決しないのか

2. **Transactional Outbox**
   - Outbox パターンで設計し直せ。outbox テーブルのカラムと、注文サービスのトランザクションで何をするかを示せ
   - outbox から Kafka へ送る方法として、**(A) ポーリング**(定期的に outbox を SELECT して送信)と **(B) CDC**(Debezium で WAL を読んで送信)を比較し、どちらを選ぶか答えよ。比較の観点には「遅延」「注文DBへの負荷」「順序」「運用で増えるもの」を含めること
   - この方式で、Kafka 上のイベントに**重複**は起きうるか。起きるならコンシューマ側はどう対処すべきか

3. **注文状況画面(Redis)への反映**
   - key=`order_id` で同じパーティションに入っているのに、注文状況サービスが**古いイベントを後から受け取る**ことがありうる。どんな場面か、少なくとも2つ挙げよ(前回の DLQ 再送も思い出すこと)
   - 古い状態に戻らないよう、Redis への書き込みをどう設計するか(イベントのどの項目を使い、どう判定するか)
   - Redis が全損したとき、どこから再構築するか。Kafka の保持期間が7日であることを踏まえて答えよ

4. **売上集計の二重計上(集計DB)**
   - 前回の問題(外部のプッシュ通知API)では「重複をゼロにはできない」という結論だった。今回の集計DBではなぜゼロにできるのか
   - 具体的な方法を1つ設計せよ(テーブル設計とトランザクションの範囲を示すこと)

5. **スキーマ進化**
   - 背景の問題4はなぜ起きたか。JSON のままでも防げたはずの実装上の原因と、仕組みとして防ぐ方法(Schema Registry と互換性モード)を説明せよ
   - `coupon_discount`(任意項目)を追加する場合と、`total_amount` を `subtotal` と `delivery_fee` に**分割して `total_amount` を廃止**する場合のそれぞれで、どの互換性モードなら通るか、プロデューサーとコンシューマのどちらを先にデプロイすべきかを答えよ

### 余裕があれば

6. **注文検索(OpenSearch)の2年分の初期投入と再構築**:Kafka には7日分しかない。新しく索引を作るとき・索引の設計(マッピング)を変えて作り直すときに、2年分のデータをどこから入れ、その間に流れてくるリアルタイムのイベントとどう整合させるか。ダウンタイムなしで新しい索引に切り替える方法も含めて述べよ

## ヒント

- 「DB のコミット」と「Kafka への送信」は別々のシステムへの書き込みで、1つのトランザクションにはできない。**1つのシステムへの書き込みに寄せる** にはどうすればよいか
- outbox のレコードと注文の更新が**同じ DB トランザクション**に入れば、「片方だけ成功」は起きない
- `event_id` は重複判定に、`version` は**新旧の判定**に使える。この2つは役割が違う
- 外部APIと違って、自社のDBなら「処理結果」と「処理済みの記録」を**同じトランザクション**に入れられる
- Kafka の **ログコンパクション**(同じキーの最新メッセージだけを残す)を使うと、保持期間に関係なく「各キーの最新状態」を持ち続けられる
- Schema Registry の互換性モード:`BACKWARD`(新しいスキーマで古いデータを読める)、`FORWARD`(古いスキーマで新しいデータを読める)、`FULL`(両方)
