## F01: 「EVALSHA sha 1 rl:{key} 60 10 600000」とは?

**結論**: 「Valkey にあらかじめ登録してあるトークンバケットの Lua スクリプトを、キー `rl:{key}`、引数 60 / 10 / 600000 で実行する」コマンド。判定 1 回につき送るのはこの 1 コマンドだけ。

| 部分 | 意味 | スクリプト内での受け取り |
| --- | --- | --- |
| `EVALSHA` | 登録済みスクリプトを SHA1 ハッシュで指定して実行 | — |
| `sha` | スクリプト本文の SHA1(40 文字の 16 進数)。図では省略 | — |
| `1` | この後に続く引数のうち、先頭何個が**キー**か(numkeys) | — |
| `rl:{key}` | バケットのキー。`{key}` は API キー(例 `rl:{ak_123}`) | `KEYS[1]` |
| `60` | 1 分あたりの回数(rate_per_min) | `ARGV[1]` |
| `10` | バースト = バケットの容量 | `ARGV[2]` |
| `600000` | キーの TTL(ミリ秒)= 10 分 | `ARGV[3]` |

返り値 `[1, 7, 0]` は「許可(1)・残り 7 トークン・待ち 0 秒」。スクリプト本体と入出力の表は [../base/LUA_SCRIPT.md](../base/LUA_SCRIPT.md)。

**理由**:

- **`EVAL` ではなく `EVALSHA`**: `EVAL` は毎回スクリプト本文(数百バイト)を送る。`EVALSHA` は 40 文字のハッシュだけで済み、ピーク 10,000 回/秒でも転送量が小さい。サーバ側に無ければ `NOSCRIPT` エラーが返るので、そのときだけ `EVAL` で本文ごと送り直す(4.1 の `NOSCRIPT` 対策。iovalkey の `defineCommand` がこれを自動でやる)
- **numkeys(`1`)でキーを分けて書く**: Valkey は `KEYS` 側を見てどのスロット(シャード)で実行するかを決める。Serverless のプロキシもこれでルーティングする。キーを `ARGV` に紛れ込ませるとシャードが分からず、クラスタで正しく動かない
- **rate / burst を毎回引数で渡す**: ルールは DynamoDB にあり、ECS のメモリにキャッシュしている。Valkey にはルールを持たせないので、プラン変更時に Valkey を更新する処理が要らない(base Q10)
- **TTL 10 分**: しばらく使われない API キーのバケットを自動で消し、メモリを食い続けないため。burst 10・60 回/分なら 10 秒で満タンに戻るので、10 分放置されたキーは消しても「満タンから」と同じ結果になる

**トレードオフ**:

- `EVALSHA` はスクリプトキャッシュが消えると初回だけ `NOSCRIPT` → `EVAL` の往復が 1 回増える。Serverless ではキャッシュをサービスが管理しており、スケールやノード交換で消えうる(Q07)
- TTL は「満タンに戻るまでの時間(burst ÷ rate)」より長くしないと、消えたときに途中のトークン数が失われて満タン扱いになり、本来より多く通してしまう。プランで burst を大きくするなら TTL も見直す
