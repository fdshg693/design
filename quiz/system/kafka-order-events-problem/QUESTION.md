# 問題:注文イベント配信をKafkaで組む(Kafka初級)

## 背景

フードデリバリーサービス「はやメシ」では、注文の状態が変わるたびに **注文イベント** を発行し、
複数のサービスがそれを受け取って処理している。
今回、イベント配信の仕組みを Apache Kafka に置き換えることになった。

インフラチームが大枠はすでに決めている。**あなたが考えるのは「未決定」の部分だけ**でよい。

## 確定済みの構成(考えなくてよい)

```
 [注文サービス] --(produce)--> Kafka topic: order-events --(consume)--> [通知サービス]
                                                         \-(consume)--> [配達割当サービス]
                                                         \-(consume)--> [売上集計サービス]
```

| 項目 | 決定内容 |
|------|----------|
| Kafkaクラスタ | マネージドKafka、ブローカー3台(運用は考えなくてよい) |
| トピック | `order-events` の1本のみ(全イベント種別をこの1本に流す) |
| レプリケーション | replication factor = 3、`min.insync.replicas = 2` |
| プロデューサー設定 | `acks=all`、`enable.idempotence=true`(送信側の重複・欠損は対策済み) |
| 保持期間 | 7日 |
| メッセージ形式 | JSON。`event_id`(UUID)、`order_id`、`user_id`、`store_id`、`type`、`occurred_at` を含む |
| イベント種別 `type` | `CREATED` → `ACCEPTED`(店舗受付) → `PICKED_UP`(配達員受取) → `DELIVERED`、または途中で `CANCELLED` |
| コンシューマ実装 | 3サービスとも自社開発で、実装は自由に変えられる。各サービスはコンテナで水平スケール可能。1インスタンスは割り当てられたパーティションを**逐次**処理する |
| 通知サービスの構成 | 自社の通知サービスが、外部のプッシュ通知API(APNs / FCM など、自社では変更できない)を呼んでユーザーに通知を送る。通知サービスは自社管理のデータストア(Redis / RDB)を使ってよい |

## 未決定の部分(あなたが決める)

- メッセージの **キー** に何を使うか
- トピックの **パーティション数**
- 3つのサービスの **コンシューマグループ** の切り方と、インスタンス数
- **オフセットをいつコミットするか**、重複受信をどう扱うか

## 要件・数値

- ピーク時の注文数:**120 件/秒**。1注文あたり平均 **5 イベント** 発生する
- 通知サービスは1イベントの処理に平均 **50ms** かかる(外部のプッシュ通知APIを呼ぶため)
  - 配達割当・売上集計はそれより十分速いものとする
- **同じ注文のイベントは発生順に処理されなければならない**
  - 例:`CANCELLED` の後に `ACCEPTED` を処理してしまうと、キャンセル済みの注文に配達員が割り当てられてしまう
- 異なる注文同士の順序は気にしなくてよい
- 3つのサービスは **それぞれが全イベントを受け取る** 必要がある(どれか1つが受け取れば良い、ではない)
- 通知サービスがデプロイ中に落ちても、イベントを **取りこぼしてはならない**
- 同じ通知がユーザーに2回届くのは **なるべく避けたい**(絶対ではない)

## 設問

1. **メッセージキー**:`order_id` / `user_id` / `store_id` / キーなし のどれを使うべきか。理由と、他の選択肢を選んだ場合に起きる問題を1つずつ述べよ
2. **パーティション数**:ピーク時のイベント流量と通知サービスの処理時間から、最低限必要なパーティション数を計算せよ。そのうえで、実際に何個にするか(余裕をどう見るか)を答えよ
3. **コンシューマグループ**:3つのサービスのコンシューマグループをどう分けるか。また通知サービスのインスタンスをパーティション数より多く起動すると何が起きるか
4. **オフセットコミットと重複**:通知サービスはオフセットを「処理の前」と「処理の後」のどちらでコミットすべきか。それぞれで障害時に何が起きるかを比べ、選んだ方式で生じる重複をどう抑えるか述べよ

### 余裕があれば

5. 通知サービスで、外部API側の不具合により**ずっと失敗し続けるイベント**が1件あると、同じパーティションの後続イベントはどうなるか。どう対処するか(簡単な方針でよい)

## ヒント

- Kafkaは **同じパーティション内でのみ** 順序を保証する。同じキーのメッセージは同じパーティションに入る
- 1つのパーティションは、1つのコンシューマグループ内で **同時に1インスタンスにしか** 割り当てられない
- 異なるコンシューマグループは、同じトピックをそれぞれ独立したオフセットで読む
- `event_id` が何のために用意されているかを考えてみよう
