## F01: DB への書き込みは自分の投稿のときだけ? Redis は直近の特定の読み書きだけを速くしている?

**結論**:

- DB(投稿ストア・フォロー関係)に書くのは **投稿したとき** と **フォロー / 解除したとき** の 2 つだけ。フォロワーへの fan-out は DB には書かず、Redis にだけ書く
- Redis は「DB の前に置いて速くするキャッシュ」だけではない。ホームの ID 列は **DB に存在しないデータ** で、Redis にしか無い(DB から作り直せる派生データ)。速くしているのは主に **ホームの読み** で、書き込み(投稿の保存)は速くしていない

**理由**:

イベントごとの書き先:

| イベント | DB に書くもの | Redis に書くもの |
| --- | --- | --- |
| 投稿 | 本文 + その人の投稿索引(同期) | 自分の `timeline`(同期)、セレブなら `celebrity_posts` |
| fan-out | なし | フォロワー全員の `timeline` に ZADD |
| フォロー / 解除 | FOLLOW の行、`follower_count`、`is_celebrity` | フォロー中キャッシュを捨てる |
| ホーム取得 | なし | キャッシュミスした本文・フォロー中一覧を詰める |

Redis の中身は役割が 2 種類ある:

| 中身 | 種類 | DB にある? |
| --- | --- | --- |
| `timeline:{user}`(直近 200 件の ID) | 実体化したビュー。ホームはここを読むのが本線 | 無い。フォロー中の投稿索引から作り直す(→ Q03) |
| `celebrity_posts`(直近 200 件) | 実体化したビュー | 無い。セレブの投稿索引から作り直せる |
| 本文(TTL 1 日)、フォロー中一覧(TTL 1 時間) | 普通の read-through キャッシュ | ある(正本は DB) |

- fan-out を DB でやると、20 投稿/秒 × 100 人 = 2,000 行/秒の書き込みが、正本と同じストアに乗る。しかもその行は 200 件で刈り込まれて消える使い捨て。消えても作り直せるので、耐久性の高い DB に置く必要がない
- 「直近」に絞っているのはその通り。ホームは 200 件まで、本文は 1 日で期限切れ。プロフィールや古い投稿は Redis を通らず DB を読む
- 投稿の保存は DB への同期書き込みのままで、Redis で先に受けて後から DB に流す(write-behind)ことはしない。投稿を失うと戻せないため

**トレードオフ**:

- Redis が消えると、ホームは DB から作り直すまで遅い(フォロー数ぶん索引を読む)。データ自体は失わない(→ Q13)
- fan-out 先が Redis だけなので、Redis のメモリ(約 40GB)が DAU とフォロー数に比例して増える
