# 設計の読み解き

AI が**完成済みの設計**(Mermaid 図 + 簡単な説明)を用意し、ユーザーはそれを読んで分からないことを質問しながら学ぶ
`projects/`(一緒に設計する)や `quiz/`(ユーザーが解く)と違い、ここではユーザーは設計しない。読み手・質問者に徹する

## フォルダ構成

```
readings/
  _template/              # 雛形(新規作成時にコピーする)
    README.md             # 題材の目次用
    base/                 # base 用
    variant/              # バリアント用
  <トピック>/
    <題材名>/
      README.md           # 題材の目次(バリアント一覧と進捗)
      base/               # 基礎となる構成(特定のクラウド・製品に依存しない)
        README.md         # 概要・前提・読む順番・進捗
        DESIGN.md         # 完成済みの設計(Mermaid 図 + 説明)
        QUESTIONS.md      # あらかじめ用意した質問集
        QA.md             # 質問と回答のログ
        resource/         # 調査結果(必要な場合のみ)
      <バリアント>/        # base を元にした派生(例: aws / azure / advanced)
        (base と同じファイル構成)
```

- トピックは `quiz/` と同じ(`system` / `front` / `db` / `api` / `infra` / `security`)
- 題材名は英小文字のケバブケース(例: `url-shortener`)

## base とバリアント

1 つの題材を「基礎となる構成(`base/`)」と、それを元にした「バリアント」に分ける。base だけでは足りない具体的なサービスの詳細や発展的な要件は、バリアントで学ぶ

- `base/`: 題材の基礎。特定のクラウドに依存させない
    - コンポーネントは「KV DB」「キャッシュ」「メッセージキュー」などの種類や、Redis のような一般的な技術名で書く
    - クラウドのマネージドサービス名(DynamoDB など)は「例」として添える程度に留め、詳細はバリアントに回す
- バリアント: base の設計を元に、何か 1 つの軸で具体化・発展させたもの
    - フォルダ名の例(これに限らない。作るときに都度決める。英小文字のケバブケース)
        - `aws` / `azure` / `gcp`: base の抽象コンポーネントを特定クラウドのサービスに置き換え、サービス固有の設定・制約・上限・料金を学ぶ
        - `advanced`: 要件や規模を引き上げる(マルチリージョン、100 倍の規模など)
    - 1 バリアントの軸は 1 つに絞る(組み合わせが必要なら、それ自体を 1 バリアントとして名前を付ける。例: `aws-multi-region`)
    - base の内容は繰り返さず、**差分だけ**を書く。前提・要件は変えたものだけ書き、それ以外は base を引き継ぐ
    - 読む前提は「base を読み終えていること」
- バリアントは base を書き換えない。バリアントの検討で base の不備が見つかった場合は、base の `QA.md` に「改善案」として残す
- base への質問で特定サービスの話になる場合は、簡潔に答えたうえで「詳細は `aws/` で」のようにバリアントへ誘導してよい(まだ無ければ作成を提案する)

## ファイル

- 題材直下の `README.md`: 題材の目次
    - フロントマターは `summary` と `topic` のみ
    - バリアント一覧の表(フォルダ・内容・level・status)を置き、バリアントを追加したら行を足す。status は各フォルダの README と揃える
- 以下は `base/` と各バリアントのフォルダ内のファイル
- `README.md`
    - 先頭に以下のフロントマターを付ける
        - `summary`: 題材の概要(1文)
        - `topic`: トピック(トピックフォルダ名と一致させる)
        - `level`: レベル(初級 / 中級 / 上級 など)
        - `status`: 進捗(未読 / 読解中 / 一通り完了)
        - `variant`: バリアントのみ。フォルダ名と一致させる
    - 前提とした要件・規模、スコープ外、読む順番を書く
    - バリアントでは「base との違い」(追加・変更した要件、具体化した対象)を書く
- `DESIGN.md`: AI が書く完成済みの設計
    - base: 「全体構成図 → 主要フローのシーケンス図 → コンポーネントごとの説明 → 設計判断の要約」の順
    - バリアント: 「base との対応表 → 全体構成図 → 変わったフローのみ → サービス固有の詳細 → 設計判断の要約」の順
    - 説明は簡潔に。理由の詳細は質問されたときに `QA.md` で答える(最初から全部書かない)
    - 図は Mermaid。1 図に詰め込みすぎない
    - 図や説明の要素には `QUESTIONS.md` の質問 ID を `(→ Q03)` のように添えて、疑問が湧きそうな箇所から質問に飛べるようにする
- `QUESTIONS.md`: 質問が浮かばないとき用の質問集
    - 下記カテゴリごとに、ID 付きのチェックリストで並べる(回答は書かない)
    - 各カテゴリ 2〜4 問程度。易しい順に並べる
    - 質問 ID はフォルダ(base / 各バリアント)ごとに Q01 から振る。別フォルダの質問を参照するときは `base Q03` のように書く
    - バリアントの質問は、base では答えられないもの(サービス固有の挙動、追加要件の影響)に絞る
- `QA.md`: 質問と回答のログ
    - ユーザーが質問したら、AI が回答をここに追記する(質問集の ID があれば見出しに付ける。自由質問は `F01` などの連番)
    - 回答後、`QUESTIONS.md` の該当チェックを付ける
    - 回答で設計の不備が見つかった場合は `DESIGN.md` を直さず、`QA.md` に「改善案」として残す(元の設計と比較できるように)
- `resource/`: 公式ドキュメントなどの調査結果
    - あくまで、ユーザーに質問された内容だけを記載する

## 質問集のカテゴリ

| カテゴリ | 内容 |
| --- | --- |
| 理解確認 | 図の各要素の役割、データの流れ |
| なぜ | この技術・構成を選んだ理由 |
| エッジケース | 境界値、競合、重複、異常入力 |
| 障害 | コンポーネントが落ちた/遅くなったときの挙動 |
| スケール | 10 倍・100 倍になったときにどこが詰まるか |
| 別の設計 | 他の選択肢と比べた場合のトレードオフ |
| 発展 | 要件が追加されたらどう変えるか |

- 該当しないカテゴリは省略してよい。必要に応じて追加する

## 進め方

- AI は「設計者本人」として振る舞い、質問に答える
    - 回答は結論 → 理由 → トレードオフの順。必要なら図を添える
    - 設計の弱点を聞かれたら隠さず認める
    - 回答の最後に、関連する次の質問を 1〜2 個提案してよい
- 題材作成時は `_template/README.md` を題材直下に、`_template/base/` を `base/` としてコピーし、`DESIGN.md` と `QUESTIONS.md` まで AI が書く。`QA.md` は空で始める
- バリアント作成時は `_template/variant/` を `<バリアント>/` としてコピーし、同様に書く。題材直下の `README.md` の表に行を足す
    - クラウドのバリアントでは、サービスの仕様・上限・料金は公式ドキュメントで確認してから書き、出典を添える
- 数値(見積もりやスペック)は根拠・前提を併記する
- 関連する `../projects/` / `../quiz/` / `../services/` があればリンクする

- WEB 検索には `web-lookup` スキルがおすすめ
