# URL 短縮サービス AWS 版の設計 構成案

## 全体の流れ

まず URL 短縮サービスの要件・規模と、クラウドに依存しない基本設計(ID 生成・キャッシュ・非同期集計)を説明する(base の内容)→ 構成要素ごとに AWS サービスを選んだ理由と全体構成を示す → 主要フロー(採番・作成・リダイレクト・集計)を AWS のサービス固有の工夫込みで 1 枚ずつ → 設定値と月額の概算 → 設計判断のまとめ

- 聞き手は base を読んでいないので、「base との差分」という言い方はしない。base の内容は前半で説明し、AWS 版の設計として一続きに見せる

### 2. どんなサービスか

- メッセージ: 長い URL を 7 文字の短い URL に変え、アクセスされたら元の URL へリダイレクトする
- 内容:
    - 例: `https://sho.rt/aZ3k9Qx` → 元の長い URL
    - 機能: 短縮 URL の作成 / リダイレクト / 有効期限(任意)/ クリック数の集計(数分遅れで良い)
    - スコープ外: ユーザー認証・管理画面、不正 URL の検査、マルチリージョン
- 図: なし
- 話すこと: 主題は「ID の作り方」と「大量のリダイレクトをどう速く返すか」

### 3. 要件と規模

- メッセージ: 読み(リダイレクト)が書き(作成)の 100 倍あり、5 年で 16 億件・800GB になる
- 内容:
    - リダイレクト: p99 50ms 以内、可用性 99.99%(作成側は 99.9%)
    - 作成 平均 10 件/秒、リダイレクト 平均 1,000 件/秒・ピーク 5,000 件/秒
    - 保存件数 10 件/秒 × 5 年 ≒ 16 億件、1 件 500B として約 800GB
    - 短縮 URL は推測されにくくなくて良い(公開リンク前提)
- 図: なし
- 話すこと: この「読み:書き = 100:1」と「推測されにくさ不要」が以降の設計判断の根拠になる

### 4. 基本の設計方針

- メッセージ: 連番 + Base62 で ID を作り、キャッシュで読みを吸収し、集計は非同期にする
- 内容:
    - ID: 連番を Base62 に変換(7 文字で 62^7 ≒ 3.5 兆通り。16 億件に十分)→ 衝突チェック不要
    - 採番: API サーバが 1,000 個ずつブロックで予約し、メモリで払い出す → 採番 DB の負荷は 1/1000
    - 読み: キャッシュで吸収(読み:書き = 100:1)
    - 集計: キューに投げて非同期 → リダイレクトを遅らせない
    - リダイレクトは 302(集計を取りこぼさない)、期限切れは 410 Gone
- 図: 新規: base DESIGN.md 1 章の全体構成図(抽象コンポーネント版)を簡略化したもの
- 話すこと: ここまではクラウドに依存しない設計。次から各部品を AWS のサービスに置き換える

### 5. 構成要素と AWS サービスの選定

- メッセージ: 8 つの構成要素を AWS のマネージドサービスで実現し、データストアは DynamoDB に寄せた
- 内容: aws DESIGN.md 1 章の対応表を「構成要素(役割) / AWS サービス / 選んだ理由」で表示。関連質問列は省く
- 図: なし(表)
- 話すこと: 採番は RDB のシーケンスでも作れるが、アクセスは 100 秒に 1 回程度なので、そのために RDS を持つより DynamoDB のカウンタで済ませた

### 6. 全体構成(AWS)

- メッセージ: データストアを DynamoDB に一本化し、VPC エンドポイントで NAT を通さない
- 内容:
    - DynamoDB は Gateway Endpoint(無料)、SQS は Interface Endpoint
    - クリックは API タスクで 1 秒ぶん溜めて SQS にまとめて送る
- 図: aws DESIGN.md 2 章の全体構成図(ほぼそのまま。DLQ は残す)
- 話すこと: 同期パス(Route 53 → ALB → ECS → Valkey / DynamoDB)と非同期パス(SQS → Lambda → click_stats)を分けて説明。スライド 4 の図と見比べてもらう

### 7. 採番: DynamoDB のアトミックカウンタ

- メッセージ: `UpdateItem ADD` はアトミックなので、複数タスクが同時に取ってもブロックは重ならない
- 内容:
    - 1 回で 1,000 件ぶんのブロックを確保
    - 書き込みは 10 件/秒 ÷ 1,000 = 0.01 回/秒 → 1 パーティション上限(1,000 WCU/秒)に遠く及ばない
- 図: aws DESIGN.md 3.1 のシーケンス図
- 話すこと: 1 アイテムへの書き込み集中(ホットキー)が気になるが、頻度が低いので問題にならない

### 8. 短縮 URL の作成

- メッセージ: 連番でも条件付き書き込みで上書きを防ぎ、有効期限は TTL 属性で持つ
- 内容:
    - 手元のブロックから ID → Base62
    - `attribute_not_exists(code)` でバグ・手動投入による上書きを防ぐ
    - `expiresAt` をエポック秒の TTL 属性として保存
    - 同じ長い URL を 2 回登録すると別のコードになる(重複排除しない)
- 図: aws DESIGN.md 3.2 のシーケンス図
- 話すこと: 本来衝突しないが、保険として条件を付けるコストはほぼゼロ

### 9. リダイレクト

- メッセージ: 結果整合性で安く読み、見つからないときだけ強い整合性で読み直す。期限はアプリで判定する
- 内容:
    - まずキャッシュ(Valkey)、ミスしたら DynamoDB
    - 結果整合性読み込みは強い整合性の半額 → 作成直後の誤 404 を防ぐために読み直す
    - TTL は即座に消さない(数日以内)→ アプリで期限判定して 410
    - キャッシュの有効期限は min(24h, 残り期限)
- 図: aws DESIGN.md 3.3 のシーケンス図(スライド用に SQS 送信の Note を簡略化)
- 話すこと: クリックはメモリのバッファに追加し、1 秒 or 100 件ごとに SendMessageBatch

### 10. クリック集計

- メッセージ: バッチで受けてキーごとに合算し、書き込み回数を減らす。ただし at-least-once なので二重加算はあり得る
- 内容:
    - バッチ最大 100 メッセージ / 最大 60 秒待ち
    - (code, day) ごとに合算して `ADD count :n`
    - 失敗分だけ `batchItemFailures` で返す
- 図: aws DESIGN.md 3.4 のシーケンス図
- 話すこと: 二重加算への対策は DESIGN.md では未解決の論点(Q09)として残している

### 11. 主な設定値

- メッセージ: AWS の上限と課金単位を踏まえて設定値を決めている
- 内容: aws DESIGN.md 4.1 の表から抜粋(オンデマンド、パーティション上限、TTL、Valkey 最小 100MB、SQS 64KB 課金単位、Lambda バッチ、可視性タイムアウト、部分バッチ応答、DLQ)。12 行のままだと溢れるので 8 行程度に絞る
